# Proposal review foundation

The local MVP scope below was agreed on 2026-11-02. The application implements the chat, source intake, staged review, and local human-decision workflow. See the task tracker for verification and independent-review status.

## Route and objective

**SDD delegated specification.** The first review spans source boundaries, structured model output, evidence judgments, bilingual UI, and a human decision. The initial fixture and output contracts are resolved here before implementation is divided into independent modules. The [product record](../../../PRODUCT.md) owns intent, the [design](design.md) owns the planned flow and data shapes, and [the project tracker](../../specs/tasks.md) alone owns task status.

The first checkpoint uses the [original synthetic proposal and source set](../../examples/support-draft-pilot/proposal.md). It is deliberately small enough to inspect by hand. The completed local MVP also accepts reviewer-provided proposals and authorized sources. External search, long-running jobs, shared runtime code from Document Intelligence, and public deployment remain outside scope.

## Observable acceptance

- **REQ-DPR-001 — bounded intake:** A reviewer can open the labeled fictional example, see its decision request and source list, and tell which inputs are missing. The fixture is never presented as real pilot evidence.
- **REQ-DPR-002 — shared evidence boundary:** Supporting and opposing passes receive the same authorized proposal and source set. Each pass is bounded; neither perspective is forced to produce the same number of arguments. A passage from another review cannot enter the current ledger.
- **REQ-DPR-003 — atomic ledger:** Each claim has a stable ID, text, `origins[]` containing one or more of `proposal`, `supporting`, or `opposing`, a kind (`factual` or `value_judgment`), and links to the arguments that use it. Extract or normalize claims from both the proposal and generated perspectives before retrieval. Repeated wording may share a claim ID without erasing its origins. Value judgments are labeled but do not receive factual evidence verdicts.
- **REQ-DPR-004 — inspectable verdict:** A factual verdict is `supported`, `contradicted`, `mixed`, or `insufficient`. It records a short rationale and supporting or contradicting passage IDs, or explicitly records that no relevant source was found. Every cited ID resolves to the same review's source and locator. ID validation alone does not establish semantic support.
- **REQ-DPR-005 — honest synthesis:** The review shows the strongest relevant arguments, evidence limits, conflicting sources, and unresolved questions. An open question names what source or clarification would help. Persuasiveness, if scored, remains separate from the factual verdict and cannot change it.
- **REQ-DPR-006 — human decision:** The reviewer can inspect passages and then record `approve`, `reject`, or `defer` with a required rationale, optional conditions, and timestamp. One current decision is stored locally per review and can be corrected by an explicit reviewer action. No outcome is preselected or saved as a model decision.
- **REQ-DPR-007 — bilingual experience:** Spanish is the initial locale, English is selectable and persists, and the selected locale is sent explicitly to every model request. UI labels, errors, and new generated text follow that locale; direct source quotations retain their original language.
- **REQ-DPR-008 — failure and reviewability:** Invalid structured output, missing passages, provider failure, or incomplete evidence produces a visible recoverable state without inventing a verdict. A reviewer can inspect the stage output and resume or retry a bounded stage without silently changing an already recorded human decision.
- **REQ-DPR-009 — evaluation gate:** Before quality claims, version labeled cases for claim support, missing counterarguments, unresolved questions, bilingual behavior, and human reviewer agreement. Report case counts and observed results; keep citation resolution and semantic support as distinct measures.
- **REQ-DPR-010 — chat-first intake:** `/` opens a conversational intake in Spanish by default. Before the first model request, the reviewer sees an external-processing notice and explicitly opts in. The assistant asks for missing decision context, then produces an editable proposal summary. If the reviewer says to stop asking questions, or the assistant has already given two clarification replies, it closes intake and leaves undecided details open in the editable summary. Review generation starts only when the reviewer selects `Generate review`; chat text alone never triggers it. The selected locale is explicit in every model request.
- **REQ-DPR-011 — reviewer sources:** The reviewer can paste source text or add bounded TXT, MD, PDF, and DOCX files. The app extracts digital text into review-owned passages with inspectable locators and keeps original source identity. A scanned PDF with no usable text gets an actionable OCR-needed message; the MVP does not promise OCR or broad format compatibility. Only explicitly authorized review sources may reach a model stage.
- **REQ-DPR-012 — local history and deletion:** Reviews, sources, stage outputs, and the current human decision are saved on local disk without user accounts. `/reviews` lists saved reviews; `/reviews/[id]` shows one review. A reviewer can delete a review and its local files from the app. Data remains until that action; no automatic retention period is claimed.
- **REQ-DPR-013 — provider boundary:** Groq credentials remain server-side in this project's ignored local environment, using the same `GROQ_API_KEY`, `GROQ_MODEL`, and `GROQ_BASE_URL` configuration pattern as Document Intelligence without importing its runtime code. Without a key, the labeled fictional fixture remains explorable and real generation is unavailable with a clear explanation. Provider failures and invalid structured responses are recoverable and never become evidence verdicts.
- **REQ-DPR-014 — source-free completion:** When a review has no authorized sources, each factual claim receives an explicit `insufficient` verdict with no citations, and synthesis states that the generated arguments are not evidence. Evidence and synthesis completion require no provider call, including when resuming a saved review at Evidence. Value judgments receive no factual verdict; the final human outcome remains unselected and editable.

## Development and diagram agreement

Use test-driven development for new implementation work in this project: demonstrate a failing behavior test before the code change, then a passing test and relevant integration checks. This agreement does not change Document Intelligence. Keep architecture and workflow diagrams under the project `system-design/` directory as standalone SVG, generated directly without HTML output, using the local `DESIGN.md` visual direction. The task tracker owns implementation status.

## Evidence and next step

The hand-authored example remains separate at `/example`. Real Groq runs completed the synthetic workflow in Spanish and English. A six-case evidence checkpoint found semantic errors despite structurally valid citations; recorded evaluation results must accompany any quality discussion. Browser checks cover consent, source upload, retry, citations, persistent and corrected decisions, locale, mobile layout, and deletion. Independent review findings are resolved against the canonical task tracker.
